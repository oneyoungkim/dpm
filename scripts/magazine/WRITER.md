# 매거진 글 한 편 내기 (예약 실행 순서)

하루 두 번 예약 작업이 이 문서를 그대로 따라 한다. 사람이 손으로 돌릴 때도 같다.
회차는 `morning`(아침)과 `evening`(저녁) 둘이다.

- **아침 편은 메인 이벤트 소개 글이다.** 일정에 뜨는 큰 경기·출시·발표 하나를 골라, 왜 봐야 하는지를 사실로 쌓아 소개한다(1-1).
- **저녁 편은 키워드 글("왜 난리인가") 또는 며칠 뒤에 읽어도 되는 글이다.** 단, 오늘 날짜 글 가운데 `eventIds`가 있는 글이 하나도 없으면 저녁 편이 메인 이벤트 소개를 대신 맡는다. 하루 한 편은 반드시 메인 이벤트 소개 글이 나가게 하려는 것이다.
- 어느 쪽인지는 1번 `magazine:pick` 결과의 `mainEvent.required`가 정해 준다. 직접 판단하지 않는다.

**발행 전용 폴더: `~/클로드/dpm-publish`.** 개발하는 `dpm` 폴더와 따로 둔 복제본이다. 개발 중인 변경과 섞이지 않게 하려는 것이고, 이 폴더에서는 발행 말고 아무 작업도 하지 않는다. 모든 명령은 이 폴더에서 돌린다. (순위 보조 수집 `scripts/trends/local-feed.sh`가 2시간마다 이 폴더의 코드를 읽어 쓰지만 파일은 건드리지 않는다.)

## 0. 준비

```bash
cd ~/클로드/dpm-publish     # 폴더가 없으면: gh repo clone oneyoungkim/dpm ~/클로드/dpm-publish
git status --short
git checkout main && git pull --rebase
npm ci --prefer-offline --no-audit --no-fund   # package-lock.json 이 그대로면 금방 끝난다
```

- `git status --short`에 뭔가 나오면 지난 실행이 중간에 끊긴 것이다. `git stash -u`로 치워 두고(지우지 않는다) 6번 기록에 적은 뒤 계속한다.
- 오늘 날짜로 시작하는 글이 `content/articles/`에 이미 있고 그 `publishedAt` 시각이 이번 회차(아침 = 12시 이전, 저녁 = 12시 이후)면, 이미 낸 것이니 끝낸다.
- "이미 냈는지"는 회차 시각으로만 본다. 아침 편이 나갔어도 저녁 편은 따로 낸다. 아침 편이 일정 글이 아니었는지는 1번에서 `magazine:pick`이 알아서 본다.

## 1. 글감 고르기

```bash
npm run magazine:pick -- --slot <morning|evening> --json
```

- 먼저 `mainEvent.required`를 본다.
  - `true`면 이번 회차는 **메인 이벤트 소개 글**을 쓴다. `candidates` 맨 위(`role: "main-event"`, `required: true`)가 쓸 일정이고, 그다음 두 개(`role: "alternate"`)가 대체 후보다. 맨 위 일정부터 1-1대로 쓴다. 맨 위 일정에서 근거 3개를 못 찾으면 대체 후보로 차례대로 넘어간다.
  - 세 일정을 모두 못 쓸 때만 그 아래 `role: "fallback"`("일정을 셋 다 못 쓸 때만") 후보에서 키워드 글을 고른다. 이때 6번 기록에 세 일정을 왜 못 썼는지 적는다.
  - `false`면 `mainEvent.reason`에 이유가 있다. 저녁 편이 보통 이 경우다(오늘 일정 글이 이미 나감). 아래 기준대로 키워드·상시 후보를 위에서부터 본다. 아침 편인데 `false`면 소개할 일정이 없다는 뜻이니 같은 방법으로 고르고, 기록에 그 이유를 옮겨 적는다.
- 위에서부터 본다. 고르는 기준은 하나다: **1차 자료와 언론 보도로 근거 3개를 찾을 수 있는가.** 못 찾겠으면 다음 후보로 넘어간다.
- 키워드 순위에서 온 글감은 "주식", "AI"처럼 넓은 낱말이다. 그 낱말 뒤에 있는 **이번 주의 구체적인 사건**을 찾아야 글이 된다. `data/trends.json`의 대표 글 제목으로 무슨 일인지 짐작한 뒤, 그 일을 보도한 기사와 공식 발표를 찾는다. 한 사건이 키워드 여러 개에 걸쳐 있으면 한 글로 묶는다. 사건을 특정하지 못하면 그 키워드는 건너뛴다.
- 커뮤니티에서만 도는 이야기는 쓰지 않는다.
- 일정에서 온 글감은 실제로 그날 볼 것이 있는 일정만 쓴다(경기, 출시, 발표). "~까지 이용 가능", 협업 상품 판매 같은 항목은 건너뛰고 다음 차례 일정으로 넘어간다.
- 메인 이벤트 소개 글은 "같은 분류를 세 편 연달아 내지 않는다"와 최근 글 겹침 규칙에서 빠진다. 분류가 겹쳐도 차례대로 쓴다.
- `evergreen.json`의 숫자는 확인되지 않은 실마리다. 그대로 옮기지 않고 전부 다시 확인한다.
- `content/EDITORIAL.md` 3장(쓰지 않는 것)에 걸리는 글감은 건너뛴다. 사람의 사생활 추문이 얽힌 사건은 회사·단체가 공식으로 밝힌 내용까지만 쓴다.

## 1-1. 메인 이벤트 소개 글

`mainEvent.required`가 `true`인 회차에 쓴다. 형식은 프리뷰다.

- 뼈대는 넷이다. 소제목은 글에 맞게 짓되 이 넷이 다 들어가야 한다.
  1. **무엇이 걸렸나.** 타이틀, 순위, 진출권, 기록. 이 경기·출시·발표가 끝나면 무엇이 달라지는지.
  2. **여기까지 온 길.** 지난 맞대결, 최근 흐름, 당사자가 실제로 한 말.
  3. **숫자 셋 이상.** 전적, 기록, 제원. 셋이 넘으면 표로 놓는다.
  4. **언제 어디서 보나.** 한국 시간, 중계·공식 공지.
- 서사는 사실로만 만든다. 지어낸 대결 구도, 확인 안 된 불화, 배당률은 쓰지 않는다.
- 근거 3개를 못 찾으면 다음 차례 일정으로 넘어간다. 대체 후보까지 셋 다 안 되면 키워드 글로 바꾸고 6번 기록에 이유를 적는다.
- 머리말 `eventIds`에 그 일정의 id(`mainEvent.eventId`, 대체 후보를 썼으면 그 후보의 `eventId`)를 반드시 넣는다. 화면에서 일정 카드와 글을 잇는 데 쓴다. `kicker`는 "프리뷰"다. `eventIds`가 비어 있거나, 그 id가 이미 다른 글의 `eventIds`에 있으면 5번 검사가 막는다.
- 같은 일정을 두 번 소개하지 않는다. `magazine:pick`은 지금까지 낸 모든 글의 `eventIds`를 빼고 내므로 후보에 나온 일정은 아직 소개하지 않은 것이다. 이미 소개한 일정에 당일 새 사실이 생겼으면 저녁 편 키워드 글로 다룬다.

## 2. 조사

- 웹 검색과 페이지 읽기로 근거를 모은다. 순서는 주최 단체·제조사·통계 기관·공시가 먼저, 그다음이 통신사와 일간지다.
- 근거로 쓰지 않는 것: 커뮤니티 글, 나무위키, 블로그, 유튜브 댓글, 그리고 AI가 기사를 모아 다시 쓴 사이트(기사 끝에 "AI가 작성" 표시가 있는 곳).
- 최근 일은 기본 검색에 작년 기사가 먼저 나온다. 날짜를 검색어에 넣고, 그래도 안 나오면 검색을 `extended`로 돌린다.
- 본문에 쓸 숫자·날짜·이름·인용을 하나씩 적고, 옆에 그 사실이 실제로 적혀 있는 주소를 붙인다. 주소를 붙이지 못한 사실은 본문에 쓰지 않는다.
- **페이지 읽기 도구가 돌려주는 것은 요약이다.** 요약에 나온 숫자를 그대로 쓰지 말고, 쓸 숫자와 인용은 "이 숫자가 든 문장을 그대로 옮겨 달라"고 다시 물어 확인한다. 두 번 물어 숫자가 다르면 다른 매체로 한 번 더 확인하고, 그래도 다르면 쓰지 않는다.
- 통신사 원문이 안 열리면 같은 기사를 받아 실은 다른 매체에서 읽고, 근거 목록에는 실제로 읽은 주소를 적는다.
- 일정을 다루면 `data/events.json`의 날짜·시각과 주최 측 공지를 맞춰 본다. 다르면 공지를 따른다.

## 3. 쓰기

- `content/EDITORIAL.md`를 처음부터 끝까지 읽고 쓴다. 특히 5장(문장)과 6장(모양).
- 틀 만들기: `npm run magazine:new -- --title "제목" --slug 영문-slug --category 분류 [--kicker 꼬리표]`. 메인 이벤트 소개 글은 `--kicker 프리뷰`. 파일은 `content/articles/YYYY-MM-DD-<slug>.md`로 생기고 `publishedAt`은 지금 시각으로 들어간다. 머리말 형식은 `lib/articles.ts`의 `articleFrontmatterSchema`다.
- `publishedAt`은 지금 시각(한국 시간, `+09:00`)이어야 한다. 앞날 시각을 적으면 그때까지 사이트에 보이지 않는다. `draft` 줄은 넣지 않는다.
- 날짜는 "오늘", "어제" 대신 "11월 26일"처럼 쓴다.
- 본문은 2,500자 안팎을 목표로 한다. 2,000자를 겨우 넘기는 글은 한 대목이 빠진 경우가 많다.
- `sources`에는 본문에 실제로 쓴 근거만 넣는다. 읽기만 하고 안 쓴 자료는 넣지 않는다.
- `keywords`에는 이 글이 다룬 키워드 순위의 말을(상시 글감이면 그 글감의 id를), `eventIds`에는 다룬 일정의 id를 넣는다. 없으면 비운다. 메인 이벤트 소개 글은 `eventIds`를 비우지 않는다(1-1).

## 4. 사진

글마다 관련 사진을 하나 싣는다(쓰레드 첫 글에도 같은 사진을 붙인다). 사진 없는 글은 맞는 사진을 끝까지 찾지 못했을 때만 낸다.

```bash
npm run magazine:image -- "<영문 검색어>"
```

- 후보의 설명 페이지(`sourceUrl`)를 열어, 사진 속 대상이 글의 그 사람·그 물건이 맞는지 확인한다. 이름만 같은 다른 사람, 다른 연식의 차는 쓰지 않는다.
- 사진에 글과 상관없는 일반인이 크게 나오면 쓰지 않는다.
- 맞는 사진이 없으면 `image`를 통째로 뺀다. 표지는 사이트가 글자로 만든다. 다른 곳에서 사진을 가져오지 않는다.
- 인물·팀·물건 사진이 없으면 그 일이 벌어진 장소(경기장, 공장, 매장) 사진을 찾는다. 그래도 없을 때만 `image`를 빼고, 작업 기록에 "사진 없음"과 찾아본 검색어를 남긴다.

## 5. 검사와 사실 대조

```bash
npm run magazine:check -- content/articles/<파일>.md
```

1. 오류가 0이 될 때까지 고친다. 고칠 때 뜻을 바꾸거나 근거 없는 말을 새로 넣지 않는다.
2. 검사는 분량·근거 개수·문장 규칙만 본다. 사실이 맞는지는 보지 못한다. 그래서 통과한 뒤, 본문의 숫자·날짜·이름·인용을 2번에서 적어 둔 주소와 하나씩 다시 맞춘다. 근거에 없는 문장은 지운다. 매체마다 숫자가 조금 다르면 어림수로 쓰거나("1조 9,000억 원 가까이") 출처를 밝혀 쓴다.
3. 처음부터 소리 내 읽듯이 읽고, 친구에게 설명할 때 하지 않을 문장을 고친다. 고쳤으면 검사를 다시 돌린다.
4. 세 번 고쳐도 검사를 통과하지 못하거나 사실 대조에서 근거가 빠지면, 그 글 파일을 `content/articles/` 밖으로 옮기고(초안 표시로 남기지 않는다) 이번 회차는 건너뛴다.

## 5-1. 윤문(제미나이)

글은 이 작업이 쓰고 사실 대조까지 끝낸다. 제미나이에는 문장 다듬기만 맡긴다. 새 사실을 쓰게 하거나 조사를 맡기지 않는다.

```bash
npm run magazine:polish -- prompt content/articles/<파일>.md <작업폴더>
```

1. 이 컴퓨터의 구글 크롬(Claude in Chrome)에서 한다. 연결된 브라우저가 여럿이면 `list_connected_browsers`로 macOS 크롬을 고른다(웨일은 유튜브·쓰레드용이다).
2. 새 탭에서 `gemini.google.com/app` 새 채팅을 연다. 모드 메뉴에서 **심층 분석(Neon)** 을 고르고 **사고 수준 → 높음**을 고른다. 새 채팅마다 사고 수준이 낮음으로 돌아가니 매번 확인한다(버튼 이름에 "Neon 높음"이 보여야 한다).
3. 지시문(`polish_prompt.md`)은 직접 타이핑하지 않는다(한글이 깨진다). `npm run magazine:serve -- <작업폴더>`(뒤에서 돌린다)로 작업폴더를 127.0.0.1에서 내주고, 다른 탭에서 그 파일을 열어 전체 선택·복사한 뒤 제미나이 입력창에 붙인다. 붙인 뒤 입력창 글자 수(공백 빼고)와 한글 수가 `polish_meta.json`과 같은지 본다. 다르면 지우고 다시 붙인다(클립보드는 사람과 같이 쓰므로 그사이 다른 것이 복사될 수 있다).
4. 보내고 답이 끝날 때까지 기다린다(높음은 1~2분). 답의 코드 블록을 선택해 복사하고, `LANG=en_US.UTF-8 pbpaste > <작업폴더>/polish_out.md`로 받는다.
5. 반영:
   ```bash
   npm run magazine:polish -- apply content/articles/<파일>.md <작업폴더>/polish_out.md
   npm run magazine:check -- content/articles/<파일>.md
   ```
   `apply`는 숫자·따옴표 인용·영문 표기·표·소제목 수가 원문과 같을 때만 글을 고친다. 다르면 고치지 않고 종료 코드 2로 끝난다. 그때는 원문을 그대로 낸다.
6. 반영했으면 바뀐 문장을 한 번 읽고, 뜻이 달라진 곳(주어가 바뀜, 전언이 단정으로 바뀜 등)은 원문 문장으로 되돌린다. 검사를 다시 통과해야 낸다.
7. 크롬이 연결되지 않았거나 제미나이가 답하지 않으면 윤문 없이 낸다. 기록에 "윤문 못 함"과 이유를 적는다.

## 6. 발행과 기록

```bash
git add content/articles/<파일>.md docs/magazine-log.md
git commit -m "매거진: <제목>"
git push            # 거절되면 git pull --rebase 뒤 다시, 두 번까지
```

- 푸시하면 버셀이 다시 배포하고 몇 분 뒤 사이트에 뜬다.
- 배포 확인 뒤 `npm run seo:indexnow -- https://gak.gg/magazine/<slug>` 로 네이버·빙에 새 글을 알린다. `INDEXNOW_KEY`가 없으면 안내만 나오고 건너뛴다(발행은 그대로).
- `docs/magazine-log.md` 맨 아래에 한 줄을 더한다: 날짜, 회차, 제목(또는 "건너뜀"), 글감이 어디서 왔는지, 건너뛰었다면 이유, 확신이 덜한 대목이 있으면 그것도.
- 쓰레드에는 지금 이슈인 글만 올린다. 첫 기준은 에펨코리아 검색어 순위(fmkorea.com/best 머리의 "인기 검색어", 최근 24시간 집계)이고, 그다음이 에펨코리아 포텐 글·키워드 순위, 최근 1~2일 소식, 다가오는 메인 이벤트 프리뷰다. 화제글이라도 며칠 지난 이야기는 빼고, 상시 글감(썰·기록·장비)은 쓰레드에 올리지 않는다.
- 쓰레드 글은 `_drafts/<slug>.threads.txt`에 쓴다. 첫 글(공백 포함 480자 이하, 제미나이 윤문) 뒤에 `---`, 그 아래 "전체 글 :", `https://gak.gg/magazine/<slug>`, 사진 출처 한 줄. 올릴 때 첫 글에 글의 사진을 붙인다(웨일).
- 메인 이벤트를 맡은 회차에 일정 글을 못 냈으면 세 일정 각각을 왜 못 썼는지 적는다(예: "근거 2개뿐", "볼 것이 없는 판매 안내"). 아침 편이 못 냈으면 저녁 편이 메인 이벤트를 다시 맡는다.

## 하지 않는 것

- 글 파일과 `docs/magazine-log.md` 말고는 고치지 않는다. 검사 규칙(`scripts/magazine/rules.ts`), 편집 기준, 사이트 코드를 고쳐서 통과시키지 않는다.
- `git push --force`, 브랜치 지우기, 지난 글 지우기를 하지 않는다.
- 한 회차에 한 편만 낸다. 못 냈다고 다음 회차에 두 편을 내지 않는다.
- 바깥으로 나가는 요청에 사람 이름·이메일을 싣지 않는다.
